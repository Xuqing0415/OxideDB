# 从原型到产品：三次我改了做法

## 一、把功能放进真实形态

测试全绿只说明我写的那条路是通的，不说明那条路真的被走过。一个功能可以长期保持「从未真正执行过」的状态，而且一直是绿的。

我原来的节奏是：实现、写测试、提交。写测试的时候，我断言的是**我脑子里那个模型**——「这两个 key 在不同的分片里」——而不是**代码里那个事实**——「这两个 key 路由到哪」。两者看起来是一回事，直到它们不是。

那天我打开 `test_cross_shard_transaction.py`：断言写着 `md5(key_a) % 2 != md5(key_b) % 2`。然后我打开路由：它是区间映射。两个地方都在回答「这个 key 属于哪个分片」，而它们从未见过面——测试挑的两个 key 首字节都是 `0x6b`，按区间都落在 shard 0：那次「跨分片提交」只碰了一个 Raft group，96 个测试全绿。同一天的另一面：回滚测试回滚的是一个 PENDING 事务，`rollback()` 对 PENDING 直接返回、根本不碰分片——那两条断言的前提，就是「什么都不会变」。这两个 bug 是同一个句式：**断言的前提，恰好把断言要测的东西排除了**。

后来，断言改成走集群自己的范围映射，并且不止断言两个 key 在不同区间，还断言提交路径真的产出了两个分片、落在不同的 Raft group 上；回滚测试也补上了 prewrite。一个「两种结局都对」的测试用 `--no-bootstrap` 变成确定的。边界只有一句：**这套只在「断言走的路」和「代码走的路」是两条路时才救得了你**——测试和代码本来就是同一套逻辑时，它什么也不管。

## 二、从「修 bug」到「发现 bug 为什么可能」

有些 bug 不会以失败的形式出现。它不抛异常、不超时、也不违反任何断言——它让**不该成功的事情成功了**。

我原来的节奏是：发现 bug、修掉、补一条回归测试。这个节奏默认 bug 会自己暴露——异常、超时、断言变红，总有一个会响。但只要 bug 的表现是「一个看起来完全正常的答案」，这一整套都不会响：测试是绿的，代码审查是过的，日志里没有一行异常，而答案是错的。

那天我盯着 `responses` 看了几秒。这是修复前的真实代码（`git show b519fd0^:oxidedb/raft/node.py`）：

```python
responses = []
for peer_id in peers:
    try:
        response = self._append_entries(peer_id, current_term, next_index.get(peer_id, 1),
                                        log, leader_commit)
        responses.append(response)
    except Exception:
        responses.append(None)

with self._lock:
    if self._state != NodeState.LEADER or self._current_term != current_term:
        return ReadResult.failure(ErrorCode.ERR_NOT_LEADER, "Lost leadership during read")
```

它被创建、被填充、再也没被读过。而在整条读路径里，唯一需要被检查的东西就是它——`responses` 里到底有几个节点回应了我。收集了多数派响应却不数，等于没有多数派：一个已经被废黜的领导者照样会回答，而这个答案**和正确的那个长得一模一样**。这段代码有 RPC、有锁、有错误处理、有并发复查，看起来和 ReadIndex 没有任何区别；它能骗过代码审查、骗过 96 个测试，因为它缺的不是代码量，是一个判断。

修好之后，同一个循环里只多做了一件事：`acks = 1`，每收到一个响应 `acks += 1`，然后 `if acks < majority` 就直接拒绝——从「收集」到「检查」，差的只是这一行。

后来我在另外两处看到了同一个形状：`freeze` 冻结对了组，靠的是两条语句碰巧的顺序，换个顺序就会冻结整个集群（`abc5306`）；一条 move 记录同时回答两个生命周期不同的问题，删早了一步，publisher 就把刚落地提案写的集合覆盖回了路由表（`456cd37`）。

做法上改的只有一件：**断言的目标从「能不能成功」换成「什么情况下必须失败」**，并开始把「一旦不成立就会静默地错」的东西写成清单（`de01143` 的五条不变量）。这个转折的边界很清楚——它只对表现为「太成功」的 bug 有用；报错、超时、挂死的 bug，老办法照旧抓得到。

## 三、从「自己验证」到「验证自己的验证」

我做对照实验的方式是：删掉一段代码，看测试红不红。这个动作有一个从来没被验证过的前提——**删除真的发生了**。一旦它不成立，实验就是绿的，而绿正是「验证通过」的样子，你不会再看第二眼。

我原来的做法是：改动、删掉要验证的那段、跑测试、看到红、收工。整条链上没有一步在问「我的删除生效了吗」。它大多数时候是对的，因为一个真的执行了的删除通常会让某些东西变红；问题在于「通常」和「总是」之间的距离，恰好是这条做法失效的地方。

`a567412` 那次用了两个探针。第一个在 `_move_row_via_wire` 顶部抛异常：用它的 4 个测试红了，另外 3 个没红——这正是它该有的样子，也正因为如此，它证明了自己落对了地方（探针要是插歪了，7 个会一起绿）。第二个更像一把尺子：把那一行 `start_ts` 换成 `None`——**target 里每一个值、每一个版本都还是原来的样子**，唯一不同的是写下去的命令字节。测试红了，而且只红在字节断言上。如果它不红，那条「命令字节必须一致」的断言就只是装饰。

`a8deb28` 那次是另一头：实验做完要还原。`git diff` 打开，空的。你以为文件回去了，但文件并没有——它多了一个裸换行、少了一个空行，而 `core.autocrlf` 让 git 比较的是归一化之后的形式，所以 diff 看不见。整件事里唯一露出马脚的，是 git 关于行尾的那条警告。

同类的还有两处：探针插进了 docstring（`f31f694`）——一次从未被执行的删除；`tests/_cluster.py` 里 33 行 `\r\r\n`（`c17d96c`）——文件自己的行尾在 blob 里又复制了一份，修好了还会回来。

后来做法上变了三件。注入按职责来：一个职责一次注入，因为一条测试里第一条红的断言回答的是「实验走了多远」，不是「测试有多深」。还原的判据从 `git diff` 换成和 `git show HEAD:<path>` 比字节。而「N 次注入，各自只红自己那条」成了提交信息的固定栏目——09-20 到 09-21 两天里，这样的提交有 9 条。这套做法只在「改动看起来是对的」时有用：改动看起来就可疑的时候，你本来就会去验它，不需要再给自己设一个探针。

最后是关于这一节自己的。我记了很久的一句话是「两种破坏，都停在 377」。为了写这篇文章重跑一遍：377 还在，但和整段破坏撞在同一条断言上的是「跳过抛温」，不是记忆里的「不写 note」——四个职责里有三个各有自己的断言，而记忆把那次实验压成了两句话。这提醒我的不是「记忆不可靠」这么泛的结论，而是：**验证过代码，不等于验证过你对那次验证的记忆**——记忆里的行号是活的，git 里的行号是死的。

## 后记

有三处事实我一直没想好放哪。探针插进 docstring 那一次，现在只是 `docs/design.md` 里一个从句里的例子，不是一个事件。还原分支坏掉的那两次没有住处——跑注入的是仓库外的临时脚本，225 个提交里没有一个字提到它。它们教出来的东西——编辑前后比 sha256——只有规则的样子活了下来。

它们和那些有 hash 的事实是同一类东西，只是没被留下来：**事件被推广成规则时，事件本身消失了**。规则活在文件里，事件只活在「我当时记得」里。所以我写这篇文章不是为了复述规则，是为了记下规则诞生时的样子。三个月后，规则还在，那一刻只活在这篇文章里。
